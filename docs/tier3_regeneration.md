# Tier 3 reference-CSV regeneration

Tier 3 cross-validation tests in `crates/jeod_runner/tests/tier3_*.rs` and
`tests/bevy_parity_*.rs` compare our propagated trajectories against
reference CSVs generated by the corresponding NASA-JEOD Trick verification
sims. The CSVs live in `test_data/` and are committed to the repository.

This document covers how to regenerate them — typically when JEOD bumps a
gravity coefficient file, when a new sim is added to
`trick/generate_references.sh`, or when a contributor needs to verify that
a CSV is still bit-stable after a Trick / JEOD upgrade.

## TL;DR

```bash
cargo xtask regenerate-tier3            # incremental — skips existing CSVs
cargo xtask regenerate-tier3 --force    # regenerate everything
cargo xtask regenerate-tier3 --build    # force rebuild jeod-trick first
cargo xtask --help                      # full help
```

The `xtask` wrapper builds the `jeod-trick` Docker image on first use,
mounts `test_data/` as the output directory, mounts the regeneration
script read-only, and runs the container. Output CSVs land in
`test_data/{sim_label}_{run}.csv`.

For the explicit Docker invocation (e.g. CI or environments without
cargo) the equivalent is in `CLAUDE.md` "Generating Tier 3 Reference Data".

## Prerequisites

- `docker` on the PATH.
- JEOD and Trick checkouts as siblings of `bevy_jeod`, per `CLAUDE.md`
  "Environment Setup":
  ```
  /your/parent/dir/
    bevy_jeod/    ← this repo
    jeod/         ← github.com/nasa/jeod, tag jeod_v5.4.0
    trick/        ← github.com/nasa/trick
  ```
- `.cargo/config.toml` copied from `.cargo/config.toml.example` so
  `cargo xtask` is aliased and `JEOD_HOME` / `TRICK_HOME` resolve.

## Incremental vs force-regenerate

`generate_references.sh` is **incremental by default**: for each sim, it
checks whether `${label}_*.csv` already exists in `/output` and skips the
expensive `trick-CP` build + sim run when it does. Adding a new sim to
the script and re-running picks up only the new sim.

Pass `--force` (which sets `FORCE=1` in the container) to regenerate
everything. Use this when:

- A JEOD source-data file changed (gravity coefficient, leap-second
  table) and existing CSVs may be stale.
- A Trick or JEOD version bump might have changed numerical output.
- You're investigating bit-stability across hosts.

## Adding a new sim

1. Add the sim's `run_sim` invocation to `trick/generate_references.sh`
   (model on the existing entries — choose between `run_sim_serial`,
   `run_sim_throttled`, or the SIM_dyncomp shared-build pattern based
   on whether the sim's S_define is shared with others).
2. Run `cargo xtask regenerate-tier3` (incremental will skip existing
   sims and run only the new one).
3. Verify the new CSV(s) appear in `test_data/`.
4. Add the corresponding `tier3_*.rs` test under
   `crates/jeod_runner/tests/` consuming the new CSV — typically as a
   `VerificationCase` one-liner via `recipes::verification`.

## Troubleshooting

### `image jeod-trick not found`

The `xtask` wrapper auto-builds the image on first use, but if the
build step fails or you want to rebuild from scratch:

```bash
cargo xtask regenerate-tier3 --build
```

### `Error: /generate_references.sh not found in the container.`

The image's wrapper entrypoint prints this when run without bind-mounting
the regeneration script. The `xtask` wrapper handles the mount
automatically; this message only appears if you invoke `docker run`
directly without the `-v .../generate_references.sh:/generate_references.sh:ro`
flag (or if you copied an outdated incantation from earlier docs that
predate #86).

### `No such file or directory: ../jeod` or `../trick`

The Docker build expects `jeod/` and `trick/` as siblings of the
`bevy_jeod` working directory (see "Prerequisites" above). The Docker
build context is the parent directory so both can be COPYed into the
image.

### Sim builds fail with OOM

`trick-CP` is memory-hungry (~1–2 GB per concurrent build). The
regeneration script throttles concurrent builds via the `MAX_PARALLEL`
env var (default 4). Lower it via the wrapper if you hit OOM:

```bash
cargo xtask regenerate-tier3 --max-parallel 1
```

The equivalent direct `docker run`:

```bash
docker run --rm -e MAX_PARALLEL=1 \
  -v "$(pwd)/test_data:/output" \
  -v "$(pwd)/trick/generate_references.sh:/generate_references.sh:ro" \
  jeod-trick
```

## Why generate-then-commit?

Tier 3 reference data is committed verbatim rather than regenerated in
CI for two reasons:

1. **Independence**: per CLAUDE.md "Computational Independence", JEOD
   reference data is used **only** for comparison in tests. Generating
   it in CI couples our test infrastructure to JEOD's build environment.
2. **Reproducibility**: committed CSVs let any contributor re-run Tier 3
   without setting up Docker / Trick / JEOD. A reviewer who wants to
   verify a baseline-tightening PR doesn't need to first build the
   jeod-trick image.

The cost of committed CSVs is ~150 MB of binary-text in the repo. Worth
it for the reproducibility guarantee.
