jeod_runner vs Bevy ECS — Configuration Comparison

Side-by-side comparison of how the same physics scenarios are configured in jeod_runner (standalone batch runner) and bevy_jeod (Bevy ECS integration). Both call identical jeod_sim physics functions and produce bit-identical results.

Architecture Overview

jeod_runner — Standalone Runner

  • Monolithic Simulation struct owns all state
  • Bodies in Vec<SimBody>, sources in Vec<GravitySourceEntry>
  • Global config as fields on Simulation
  • Sources referenced by usize index
  • Imperative API: add_source() → add_body() → validate() → step()
  • Pipeline order hardcoded in step_internal()
  • Best for: batch scripts, Tier 3 tests, standalone tools

bevy_jeod — Bevy ECS

  • State decomposed into components on entities
  • Sources and bodies are entities with opt-in components
  • Global config as Bevy Resources
  • Sources referenced by Entity handle
  • Declarative API: spawn entities → insert resources → add JeodPlugin
  • Pipeline order via ScheduleSet ordering in FixedUpdate
  • Best for: interactive apps, realtime visualization, games

Scenario A: ISS Circular Orbit

Point-Mass 6-DOF ▾

jeod_runner

let (mut sim, earth_idx) = new_sim_earth(DT);

sim.add_body(SimBody {
    trans: iss_trans(),
    rot: Some(tumble_rot()),
    mass: Some(iss_mass()),
    config: DynamicsConfig {
        translational_dynamics: true,
        rotational_dynamics: true,
        three_dof: false,
    },
    gravity_controls: GravityControls {
        controls: vec![
            GravityControl::new_spherical(earth_idx, false),
        ],
    },
    ..Default::default()
});

sim.validate().unwrap();
sim.step_n(100);

Bevy ECS

app.add_plugins(bevy_jeod::JeodPlugin);

let planet = app.world_mut().spawn((
    GravitySourceC(earth_source()),
    SourceInertialPositionC::default(),
    TranslationalStateC::default(),
)).id();

let vehicle = app.world_mut().spawn((
    TranslationalStateC(iss_trans()),
    RotationalStateC(tumble_rot()),
    MassPropertiesC(iss_mass()),
    DynamicsConfigC(DynamicsConfig {
        translational_dynamics: true,
        rotational_dynamics: true,
        three_dof: false,
    }),
    GravityControlsC(GravityControls {
        controls: vec![
            GravityControl::new_spherical(planet, false),
        ],
    }),
    GravityAccelerationC::default(),
    TotalForceC::default(),
)).id();

step_bevy(&mut app, 100);
Key difference: jeod_runner references sources by usize index; Bevy uses Entity handles. Bevy requires explicit output components (GravityAccelerationC, TotalForceC).

Scenario B: Drag + Exponential Atmosphere

Aero 6-DOF ▾

jeod_runner

let mut sim = Simulation::new(time, DT);

// Atmosphere is a field on the Simulation
sim.atmosphere = Some(AtmosphereConfig {
    model: AtmosphereModel::Exponential(
        ExponentialAtmosphere::default()
    ),
    r_eq:  6_378_137.0,
    r_pol: 6_356_752.3,
    planet_omega: 0.0,
});

let earth_idx = sim.add_source(/* ... */);

// Drag config is a field on the body
let mut body = new_sim_body_sixdof(earth_idx, false);
body.drag = Some(DragConfig {
    cd: 2.2,
    area: 1000.0,
    constant_density: None,
});
body.atmospheric_state = Some(Default::default());
sim.add_body(body);

sim.validate().unwrap();
sim.step_n(NUM_STEPS);

Bevy ECS

app.add_plugins(bevy_jeod::JeodPlugin);

// Atmosphere is a global Resource
app.insert_resource(AtmosphereModelR {
    config: AtmosphereConfig {
        model: AtmosphereModel::Exponential(
            ExponentialAtmosphere::default()
        ),
        r_eq:  6_378_137.0,
        r_pol: 6_356_752.3,
        planet_omega: 0.0,
    },
    planet_entity: None,
});

// Drag config is a per-entity component
let vehicle = app.world_mut().spawn((
    /* ...state & dynamics components... */
    DragConfigC(DragConfig {
        cd: 2.2,
        area: 1000.0,
        constant_density: None,
    }),
    AtmosphericStateC::default(),
    AerodynamicForceC::default(),
)).id();

step_bevy(&mut app, NUM_STEPS);
Key difference: Both treat atmosphere as global and drag as per-body. The mapping is direct: sim.atmosphere ↔ AtmosphereModelR resource, body.drag ↔ DragConfigC component. Bevy needs an extra AerodynamicForceC output component.

Scenario C: Spherical Harmonics 4×4 + Earth Rotation

SH Gravity RNP ▾

jeod_runner

let sh_data = load_from_jeod_cc(&path)
    .expect("load GGM02C");

let earth_idx = sim.add_source(GravitySourceEntry {
    source: GravitySource {
        mu: sh_data.mu,
        model: GravityModel::SphericalHarmonics(
            Box::new(sh_data)
        ),
    },
    // Rotation config + initial matrix together
    t_inertial_pfix: Some(DMat3::IDENTITY),
    rotation_model: RotationModel::EarthRNP,
    ..Default::default()
});

sim.add_body(SimBody {
    gravity_controls: GravityControls {
        controls: vec![
            GravityControl::new_nonspherical(
                earth_idx, 4, 4, false
            ),
        ],
    },
    ..Default::default()
});

Bevy ECS

let sh_data = load_from_jeod_cc(&path)
    .expect("load GGM02C");

let planet = app.world_mut().spawn((
    GravitySourceC(GravitySource {
        mu: sh_data.mu,
        model: GravityModel::SphericalHarmonics(
            Box::new(sh_data)
        ),
    }),
    SourceInertialPositionC::default(),
    TranslationalStateC::default(),
    // Config and output are separate components
    RotationModelC(RotationModel::EarthRNP),
    PlanetFixedRotationC(DMat3::IDENTITY),
)).id();

let vehicle = app.world_mut().spawn((
    /* ...state components... */
    GravityControlsC(GravityControls {
        controls: vec![
            GravityControl::new_nonspherical(
                planet, 4, 4, false
            ),
        ],
    }),
)).id();
Key difference: jeod_runner bundles rotation config (rotation_model) and output matrix (t_inertial_pfix) in one struct. Bevy separates them: RotationModelC (config) vs PlanetFixedRotationC (output, updated each step).

let tidal_config = TidalConfig {

Key difference: Same config/output separation pattern as rotation: jeod_runner has tidal_config + delta_c20 on the same struct; Bevy splits into TidalConfigC (input) and TidalDeltaC20C (output, updated by tidal_update_system).

Scenario E: Full Stack (Drag + SRP + Gravity Torque)

Aero Flat-Plate SRP Torque ▾

jeod_runner

sim.sun_source = Some(sun_idx);
sim.atmosphere = Some(atmos_config);

let mut body = new_sim_body_sixdof(earth_idx, true);

// All interaction configs are fields on SimBody
body.drag = Some(DragConfig {
    cd: 2.2,
    area: 1000.0,
    constant_density: None,
});
body.flat_plate_state = Some(FlatPlateState {
    plates: srp_plates,
    temperatures: vec![270.0],
    t_pow4_cached: vec![270.0_f64.powi(4)],
});
body.compute_gravity_torque = true;
body.atmospheric_state = Some(Default::default());

sim.add_body(body);

Bevy ECS

// Sun is its own entity with a marker
app.world_mut().spawn((
    SunMarker,
    TranslationalStateC(/* sun state */),
));

app.insert_resource(AtmosphereModelR {
    config: atmos_config,
    planet_entity: None,
});

// Each interaction is a separate component
let vehicle = app.world_mut().spawn((
    /* ...state & dynamics... */
    DragConfigC(DragConfig {
        cd: 2.2, area: 1000.0,
        constant_density: None,
    }),
    AtmosphericStateC::default(),
    AerodynamicForceC::default(),
    FlatPlateConfigC(FlatPlateState {
        plates: srp_plates,
        temperatures: vec![270.0],
        t_pow4_cached: vec![270.0_f64.powi(4)],
    }),
    RadiationForceC::default(),
    GravityTorqueC::default(),
)).id();
Key difference: jeod_runner uses sim.sun_source = Some(idx) to identify the Sun; Bevy uses a SunMarker component on an entity (queried by systems). The boolean compute_gravity_torque field becomes the presence/absence of GravityTorqueC.

Scenario F: Derived States (OE, Euler, LVLH, Solar Beta)

Derived State Post-Integration ▾

jeod_runner

sim.sun_source = Some(sun_idx);

let mut body = new_sim_body_sixdof(earth_idx, false);

// Enable derived states via Option fields
body.orbital_elements_source = Some(earth_idx);
body.euler_sequence = Some(EulerSequence::ZYX);
body.compute_lvlh = true;
body.compute_solar_beta = true;
sim.add_body(body);

sim.validate().unwrap();
sim.step_n(NUM_STEPS);

// Read results from body fields
let body = sim.body(0);
let oe   = body.orbital_elements.as_ref().unwrap();
let eul  = body.euler_angles.unwrap();
let lvlh = body.lvlh_frame.as_ref().unwrap();
let beta = body.solar_beta.unwrap();

Bevy ECS

app.world_mut().spawn((
    SunMarker,
    TranslationalStateC(/* sun state */),
));

// Enable derived states by adding components
let vehicle = app.world_mut().spawn((
    /* ...state & dynamics... */
    OrbitalElementsConfigC {
        gravity_source: planet,
    },
    OrbitalElementsC::default(),
    EulerAnglesConfigC {
        sequence: EulerSequence::ZYX,
    },
    EulerAnglesC::default(),
    LvlhFrameC::default(),
    SolarBetaC::default(),
)).id();

step_bevy(&mut app, NUM_STEPS);

// Read results from components
let oe   = app.world().get::<OrbitalElementsC>(vehicle);
let eul  = app.world().get::<EulerAnglesC>(vehicle);
let lvlh = app.world().get::<LvlhFrameC>(vehicle);
let beta = app.world().get::<SolarBetaC>(vehicle);
Key difference: jeod_runner uses Option fields and booleans to opt in (compute_lvlh = true). Bevy uses component presence — adding LvlhFrameC to the entity is what enables LVLH computation. Some derived states have config+output pairs (e.g., OrbitalElementsConfigC + OrbitalElementsC).

Global Configuration: Time, Ephemeris, Polar Motion

Resources ▾

jeod_runner

// All global state are fields on Simulation
let time = SimulationTime::at_j2000(
    default_leap_second_table()
);
let mut sim = Simulation::new(time, 10.0);

sim.ephemeris = Some(load_de421());
sim.polar_motion = Some((0.0, 0.0));
sim.sun_source  = Some(sun_idx);
sim.moon_source = Some(moon_idx);

Bevy ECS

// Each global concern is a separate Resource
app.insert_resource(
    Time::<Fixed>::from_seconds(10.0)
);
app.insert_resource(
    SimulationTimeR::default()
);
app.insert_resource(
    EphemerisR(load_de421())
);
app.insert_resource(
    PolarMotionR { xp: 0.0, yp: 0.0 }
);

// Sun/Moon are entities with markers
app.world_mut().spawn((SunMarker,  /*...*/));
app.world_mut().spawn((MoonMarker, /*...*/));
Key difference: jeod_runner has a single Simulation struct with dt, time, ephemeris, polar_motion fields. Bevy distributes these across separate typed resources (Time<Fixed>, SimulationTimeR, EphemerisR, PolarMotionR). Sun/Moon go from Option<usize> indices to marker-component entities.

Structural Mapping Summary

Aspect jeod_runner Bevy ECS
Source references usize index Entity handle
Body configuration Monolithic SimBody struct Individual components per concern
Global state Fields on Simulation Bevy Resources
Opt-in features Option<T> fields, booleans Component presence/absence
Output state Fields on same struct (filled after step) Separate output components
Config/output split Colocated in one struct Separate components (e.g., RotationModelC + PlanetFixedRotationC)
Sun/Moon identity Option<usize> on Simulation Marker components (SunMarker, MoonMarker)
Pipeline ordering Hardcoded in step_internal() Declarative ScheduleSet ordering
Time step sim.step() / sim.step_n(n) run_schedule(FixedUpdate)
Validation sim.validate() before first step validate_jeod_invariants system (runs once)
Best for Batch scripts, Tier 3 tests, CLI tools Interactive apps, games, visualization
