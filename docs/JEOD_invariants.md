# JEOD Invariants Catalog

Exhaustive catalog of invariants enforced by JEOD's C++ architecture. Each has a
`Section.Item` tag (e.g., `DB.03`) for cross-referencing from our Rust source
with `// JEOD_INV: DB.03` comments. To find the JEOD source for any invariant,
grep the JEOD tree for the distinctive identifier in the invariant description
(function name, field name, error message text, etc.).

> **Phase 11 audit (#113, 2026-04-26)** — All 68 rows with Category=`runtime`
> were audited end-to-end against post-refactor enforcement sites in `crates/`
> and `src/`. The catalog is current: invariants whose violations are now
> made unrepresentable by the type system (frame mismatches, time-scale
> mismatches, `NormalizedQuat` witness, typed entry points) are already
> classified `structural` or `n/a`; invariants that remain genuine runtime
> checks (NaN/finite guards, table-bounds checks, convergence checks,
> flag-gated config) are correctly classified `enforced` or `partial`. No
> reclassifications were needed at Phase 11; future invariants follow the
> same structural-vs-runtime decision tree on addition. See
> the [Type-System wiki page](https://github.com/simnaut/astrodyn/wiki/Type-System) for the type-system architecture and
> the [Strategy wiki page](https://github.com/simnaut/astrodyn/wiki/Strategy) §8 for the refactor history.

**Categories:**
- `initialization` — checked during `initialize_simulation()` or model init
- `runtime` — checked on every relevant call during simulation
- `structural` — enforced by C++ class layout (mandatory members, inheritance)
- `consistency` — state synchronization (A must match B after mutation)
- `ordering` — method A must be called before method B

**Enforcement legend:**
- `fatal` — `MessageHandler::fail()` (aborts simulation)
- `error` — `MessageHandler::error()` (logged, may auto-correct)
- `warn` — `MessageHandler::warn()` (logged, continues)
- `structural` — C++ value member, constructor, deleted copy ctor
- `assert` — runtime assertion
- `flag-gate` — boolean flag skips code path

**Our status:**
- `enforced` — we check this invariant (with tag location)
- `partial` — partially enforced
- `deferred` — requires future infrastructure (noted which phase)
- `n/a` — not applicable to ECS architecture
- `structural` — guaranteed by Rust type system or Bevy ECS

## Fail-loudly divergence from JEOD (#485 policy)

JEOD's `MessageHandler::warn` + continue pattern is used for several numerical-
degradation events that produce subtly-wrong-but-not-NaN physics: Gauss-Jackson
corrector non-convergence (IG.36 / IG.38), bootstrap-edit non-convergence (same),
and leap-second lookup outside the table's coverage (TM.41). JEOD's policy is
"log and continue with a degraded value"; this codebase diverges by **default**
and panics instead, on the rationale that a degraded position silently
propagating through the rest of a trajectory is the silent-wrong-physics class
of failure the fail-loudly rule (CLAUDE.md "Fail Loudly") exists to prevent.

JEOD-faithful behavior is reachable per-construction via opt-in flags so that
reference runs that need bit-for-bit agreement with a JEOD verif sim can be
authored exactly:

- `GaussJacksonConfig::allow_non_convergence: bool` (default `false`) — controls
  the corrector / bootstrap-edit warn-and-continue at `src/integration.rs`.
- `LeapSecondTable::with_clamp_out_of_range(bool)` (default `false`) — controls
  the pre-first-entry / post-last-entry warn-and-clamp at
  `crates/astrodyn_time/src/leap_second.rs`.

This row is the policy umbrella; the individual catalog rows (IG.38, TM.41)
carry the per-site enforcement details and source-tag locations. Future
JEOD-faithful warn sites that fall under the same category should follow the
same shape: panic by default, opt-in flag named on the closest configuration
struct, an IG.NN / TM.NN / etc. catalog row, and a `// JEOD_INV: XX.NN` tag at
the source site under the opt-in arm.

## Section TS: Type-System Discipline

Catalogues invariants enforced by our typed-quantity / phantom-frame surface

frames — there is no compile-time guard against cross-frame mixing. We do
have such a guard, and the rules below describe the disciplines that keep
it intact across the post-#270 codebase. Source tags live next to the
canonical storage / boundary sites they enforce; the lint test in
`tests/self_ref_self_planet_discipline.rs` is the bidirectional CI guard.

| Tag | Invariant | Enforcement | Category | Our Status |
|-----|-----------|-------------|----------|------------|
| TS.01 | `<SelfRef>`, `<SelfPlanet>`, and `<MassNode>` wildcards appear **only at per-entity / mass-tree storage boundaries** (Bevy `Component`s, `Message`s, runner `SimBody`/`VehicleConfig`/`VehicleOutput` fields, the kinematic-propagation `KinematicNodeState.trans` field plus its storage-caller lift sites) and at the boundary types those storage forms wrap (e.g. `FlatPlateState<V>` inside a `FlatPlateConfigC`, `OrbitalElements<P>` inside a runner output, `TranslationalStateTyped<MassNode>` inside a `KinematicNodeState`).
